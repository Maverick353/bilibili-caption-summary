## 0. 结论速览（TL;DR）

| 维度 | 结论 |
|---|---|
| 最省事方案 | **沉浸式翻译（免费）+ 通义听悟（免费额度）**：L1 实时双语字幕直接覆盖，B 站/抖音等靠「音频捕获 + ASR」兜底 |

| B 站最优 | **直接抓官方/AI 字幕接口**（成本最低、质量最高），抓不到再降级到 ASR |
| 抖音最优 | 无稳定字幕接口，**必须走「音频捕获 + ASR」**，或第三方（提词匠/AnyToCopy/Tinrec/BibiGPT） |
| 全自建路线 | Chrome MV3 扩展（`tabCapture`）+ 本地 faster-whisper/WhisperLiveKit + LLM API，可控性最高、隐私最好、成本最低 |
| 关键取舍 | 实时性 ↔ 总结质量 ↔ 覆盖平台 ↔ 开发成本，四者不可兼得，见第 7 节三套组合方案 |

## 1. 需求拆解：三层能力与技术前提

用户需求本质是**三条可独立、也可串联的能力链**：

| 层级 | 能力定义 | 用户可感知结果 | 核心交互时机 |
|---|---|---|---|
| **L1 实时字幕** | 视频播放过程中，同步把语音转成字幕显示在画面上 | 边看边有字幕（原文或双语） | 播放中，延迟 < 1–2 秒 |
| **L2 逐字稿获取与导出** | 播放结束后拿到该视频完整文字内容（逐字稿/字幕文本），支持复制/导出 | 一份带时间戳的全文 + SRT/TXT 文件 | 播放结束后 |
| **L3 大模型总结** | 把逐字稿喂给 LLM，产出核心精华/要点/大纲 | 结构化摘要、章节、思维导图 | L2 完成后 |

### 每层的技术前提

```
L1 实时字幕  ←  音频源  →  ASR(流式)  →  字幕浮层渲染
                  ↑                ↑
        (优先级1)抓平台自带字幕/CC   (优先级2)音频捕获
                  │
L2 逐字稿    ←  (优先)平台字幕接口 JSON  →  (兜底)ASR 累积分段 + 时间戳
                  │
L3 AI总结    ←  逐字稿文本  →  LLM API（长上下文）→  摘要/Markdown/导图
```

| 技术环节 | 关键点 | 说明 |
|---|---|---|
| **音频捕获** | 浏览器 `chrome.tabCapture` / `getDisplayMedia` / OS 级回环录音 | 决定「无字幕视频」能否处理 |
| **ASR（语音识别）** | 本地（faster-whisper / whisper.cpp）或云端 API（Whisper/Deepgram/讯飞/阿里） | 决定准确率、延迟、成本、隐私 |
| **字幕接口** | 平台若已有 CC/字幕轨，直接抓 JSON 成本最低 | B 站、YouTube 有；抖音/腾讯/爱奇艺基本没有可用的公开字幕接口 |
| **LLM 调用** | 逐字稿喂给长上下文模型做摘要 | 成本极低（1 小时视频约 1 万字，总结成本 < ¥0.1） |
| **降级策略（核心）** | 优先「抓现有字幕」，抓不到才「音频捕获 + ASR」 | 见第 3.4 节 |

## 3. 从零实现的可行技术方案

### 3.1 推荐架构

```
┌─────────────────────── Chrome 扩展 (Manifest V3) ───────────────────────┐
│  ① 内容脚本 content.js：注入字幕浮层 <div>，监听视频元素                  │
│  ② 后台 background.js (service worker)：调度、消息中转（无 Web Audio）    │
│  ③ offscreen document：唯一能做 getUserMedia/Web Audio 的地方            │
└──────────────────────────────────────────────────────────────────────┘
        │ chrome.scripting / chrome.tabCapture.getMediaStreamId
        ▼
┌── 音频捕获层 ──┐   AudioWorklet 重采样为 16kHz 单声道 Int16 PCM（~4096 采样/块）
│ 标签页音频流   │   → 同时经 AudioContext.destination 回放（否则标签页静音）
└────────────────┘
        │ 分片(约 85ms/块) → WebSocket
        ▼
┌── ASR 层（二选一）──┐
│ 本地：faster-whisper │   云端：流式 ASR API（Deepgram/阿里/讯飞/Soniox）
│ / WhisperLiveKit     │
└─────────────────────┘
        │ 增量/定稿文本 + 时间戳
        ▼
┌── 字幕渲染 ──┐   ┌── 逐字稿累积器 ──┐   ┌── LLM 总结 ──┐
│ 浮层实时显示 │   │ 分段 merge→全文  │   │ 全文→摘要/导图 │
└──────────────┘   └──────────────────┘   └───────────────┘
                          │ 导出 SRT/VTT/TXT/JSON
```

### 3.2 关键 API 与代码要点

| 环节 | API / 技术 | 要点与坑 |
|---|---|---|
| 权限声明 | `manifest.json` → `permissions: ["tabCapture","offscreen","scripting","storage","activeTab"]` | MV3 必须有 `offscreen` 才能用音频 API |
| 抓取标签页音频 | `chrome.tabCapture.getMediaStreamId({targetTabId})` | **必须用户手势触发**（点扩展图标）；授权仅到页面导航为止，刷新后需重新点 |
| 真正拿流 | 在 offscreen document 中 `navigator.mediaDevices.getUserMedia({ audio:{ mandatory:{ chromeMediaSource:'tab', chromeMediaSourceId: streamId }}})` | service worker 里**没有** getUserMedia/Web Audio |
| 静音修复 | `const ctx=new AudioContext(); ctx.createMediaStreamSource(stream).connect(ctx.destination)` | 抓取后标签页会静音，必须手动回放，否则用户听不到声音 |
| 音频预处理 | `AudioWorklet`（下混单声道、重采样 16kHz、输出 Int16 PCM 分块） | 比 `MediaRecorder` 延迟更低，适合流式；`MediaRecorder` 适合录整段文件 |
| 流式 ASR | WebSocket 推送 PCM 块 → 服务端增量返回 | 延迟目标 < 500ms；>1s 体验明显变差 |
| 字幕浮层 | `chrome.scripting.executeScript` 注入 `<div>` + `requestAnimationFrame` 同步 | 注意各站点 CSS 层级/z-index 冲突 |
| 逐字稿累积 | 按 `{start,end,text}` 分段存 `chrome.storage.local` | 支持导出 SRT/VTT/TXT/JSON |
| LLM 总结 | 逐字稿 → 长上下文模型（DeepSeek/Qwen/Kimi 等） | 逐字稿先做标点/分段清洗再喂模型，效果更好 |
| 常见报错 | `"Cannot capture a tab with an active stream"` | 关闭 offscreen document 并**轮询** `chrome.tabCapture.getCapturedTabs()` 释放状态（异步释放，别用固定 timeout） |

### 3.3 各平台适配难点

| 平台 | 字幕可抓性 | 适配策略 | 主要难点 |
|---|---|---|---|
| **Bilibili（B站）** | **高（可直连接口）** | **优先直接抓字幕 JSON，成本最低** | `view` 接口拿 `cid` → `player/v2`(wbi 签名) 拿 `subtitle.subtitles` → 下载 `subtitle_url`。**必须带登录 Cookie（SESSDATA）**，匿名返回空；`subtitle_url` 是带 `auth_key` 的临时地址；批量高频会触发限流（返回空 URL / 空 body）；**AI 字幕**走 `ai_subtitle`；**硬字幕/无字幕视频无解**，只能走 ASR |
| **抖音** | **低（无稳定接口）** | 音频捕获 + ASR，或第三方（提词匠/AnyToCopy/Tinrec/BibiGPT） | 反爬强、无公开字幕接口；链接签名校验；需处理抖音 App 与网页端差异 |
| **YouTube** | **中（接口可用但接口已加固）** | `youtube-transcript-api` 或 `yt-dlp --write-auto-sub` | **2026 年 YouTube 引入 PoToken（BotGuard 防爬）**：直接请求 `timedtext` 会返回 **HTTP 200 但空 body** 或 400；数据中心 IP 被限；`youtube-transcript-api` 已跟进适配，但仍需低频率、偶需住宅 IP |
| **腾讯视频** | **低（DRM）** | 本地 whisper 对能正常播放的音频转写；或会员页内录 | Widevine DRM 加密（DASH），解密密钥仅在服务器侧；绕过 DRM 涉及法律风险，**个人自用也应避免** |
| **爱奇艺/优酷** | **低（DRM + 会员）** | 同上，只对可播放音频做本地转写 | 登录 + DRM 双重限制；破解违反 ToS 与版权法 |
| **小红书 / 快手** | **低（无字幕接口）** | 音频捕获 + ASR；或第三方文案提取工具 | 反爬、链接加密；小红书多为短视频，逐字稿价值有限 |

### 3.4 逐字稿与总结生成链 + 降级策略（核心）

```
① 尝试获取平台自带字幕
     ├─ B站：player/v2 字幕接口 JSON（需登录 Cookie）        → 命中即用（质量最高、0 成本）
     ├─ YouTube：youtube-transcript-api / timedtext(PoToken)  → 命中即用
     └─ 其他：CC/字幕轨存在则抓取
                │ 未命中 / 无字幕 / 硬字幕
                ▼
② 降级：捕获音频（tabCapture / 系统回环）→ ASR
     ├─ 实时：流式 ASR（本地 faster-whisper / 云端流式 API）→ 满足 L1
     └─ 结束后：整段 ASR → 带时间戳 SRT/JSON → 满足 L2
                │
                ▼
③ 逐字稿清洗（去口语词、加标点、分段）→ 喂 LLM → 摘要/Markdown/导图 → 满足 L3
```

**降级策略的价值**：B 站/YouTube 优先「抓字幕」可省掉 ASR 成本与错误；抖音/腾讯/爱奇艺等无字幕源才启用 ASR，保证覆盖率。

|---|---|---|---|---|---|
| **B 站** | ⭐⭐⭐⭐⭐ 高（官方/AI 字幕接口） | ✅（沉浸式翻译/听悟；接口抓取） | ✅（接口 JSON→SRT） | ✅（BibiGPT/Kimi/元宝） | 需登录 Cookie；批量限流；硬字幕无解 |

| **YouTube** | ⭐⭐⭐⭐ 较高（timedtext） | ✅（沉浸式翻译/Glarity） | ✅（youtube-transcript-api/yt-dlp） | ✅（Glarity/BibiGPT/Kimi） | PoToken 防爬；空 body；IP 限流 |
| **腾讯视频** | ⭐ 低（DRM） | ◐（需能播放音频） | ◐（本地 whisper） | ◐ | Widevine DRM、会员限制、法律风险 |
| **爱奇艺** | ⭐ 低（DRM） | ◐ | ◐ | ◐ | 登录 + DRM |

| **小红书** | ⭐⭐ 低（无接口） | ◐（音频捕获+ASR） | ◐（ASR/第三方） | ◐（BibiGPT/Tinrec） | 反爬、链接加密、短视频为主 |

## 5. 输出格式清单

| 格式 | 结构 | 适用场景 | 生成方式 |
|---|---|---|---|
| **SRT** | 序号 + `hh:mm:ss,mmm` 时间轴 + 文本 | 导入播放器/剪辑软件（Premiere/剪映）；通用字幕 | ASR 分段直接输出；B站/YouTube 字幕 JSON → 转换 |
| **VTT** | WebVTT，`hh:mm:ss.mmm` + 文本 | 网页 `<track>` 字幕、HTML5 播放器 | whisper.cpp/yt-dlp 默认输出；JSON 转换 |
| **TXT** | 纯文本（可含/不含时间戳） | 快速阅读、喂给 LLM、复制分享 | ASR 文本拼接；去时间轴 |
| **JSON（含时间戳）** | `[{start, end, text}]` | 程序化处理、二次开发、精确对齐 | ASR 原生结构化输出；平台字幕接口原始 JSON |
| **Markdown 摘要** | 标题 + 要点/章节 + 时间戳链接 | 笔记归档（Notion/Obsidian）、知识库 | LLM 对逐字稿生成 |
| **思维导图** | 层级节点 | 快速把握结构 | BibiGPT/听悟原生；或 LLM 输出 → 导图工具 |

## 6. 限制与合规风险

| 风险类别 | 具体问题 | 应对建议 |
|---|---|---|
| **DRM 加密流** | 腾讯/爱奇艺/优酷等用 Widevine 加密，密钥仅服务器侧下发；绕过 DRM 违反《数字千年版权法》第 1201 条及平台协议 | **不对 DRM 内容做解密抓取**；仅在可正常播放的范围内做本地音频转写 |
| **平台 ToS 与反爬** | 自动化抓取违反多数平台服务条款；YouTube 已上 PoToken；B站限流 | 低频率、个人自用、不商业化；保留人工兜底 |
| **版权（逐字稿二次使用）** | 逐字稿属衍生内容，**再发布/商用/二次传播需授权** | 严格限于**个人学习/笔记**；不公开传播、不搬运改编 |
| **音频捕获的浏览器权限** | `tabCapture` 需用户手势；授权仅到导航为止；抓取后标签页静音；只能抓浏览器标签页，**抓不到桌面客户端（Zoom/Teams 桌面版）** | 抓取后把音频流接回 `AudioContext.destination`；UI 明确提示「点图标启动」 |
| **ASR 准确率** | 方言、口音、背景音乐、专业术语、多语混说都会降准确率 | 优先抓官方字幕；本地可用中文专长模型（SenseVoice）；重要内容人工校对 |
| **云端延迟与费用** | 实时 ASR + LLM 均按量计费；流式中间结果重复计费会放大成本 | 只在「定稿」结果上做 downstream；选便宜模型（DeepSeek-flash/GLM-flash） |
| **中文断句与标点** | ASR 原始输出常无标点/断句差 | ASR 后接「标点/分段」后处理，或让 LLM 重排；重要稿件人工润色 |
| **隐私** | 云端 ASR/LLM 会上传音频/文本 | 敏感内容用本地 faster-whisper + 本地/自控 LLM；系统级方案（Win Live Captions）全本地 |

## 7. 推荐结论：三套最优组合方案

> 针对「个人自用 + 覆盖 B站/抖音」，按开发成本 / 覆盖平台 / 效果 / 成本对比。

| 方案 | 组成 | 开发成本 | 覆盖平台 | 实时性(L1) | 逐字稿(L2) | 总结(L3) | 费用 | 适合谁 |
|---|---|---|---|---|---|---|---|---|
| **① 零开发** | 沉浸式翻译(免费) + 通义听悟(免费额度)/BibiGPT | **0** | 高（B站/YouTube 字幕 + 任意网页音频捕获） | ✅✅ | ✅ | ✅ | 免费为主，重度用 Pro(~¥49/月) | 想立刻用、不想折腾 |
| **② 低开发** | 油猴脚本/小工具抓 B站字幕 + Kimi/DeepSeek 总结 | **低**（装脚本） | 中高（B站/YouTube 强，抖音靠第三方） | ◐ | ✅✅（B站字幕质量最高） | ✅ | ≈0（仅 LLM token，<¥1/视频） | 主要看 B站/YouTube、要干净逐字稿 |
| **③ 全自建** | 自研 MV3 扩展 + 本地 faster-whisper/WhisperLiveKit + LLM API | **高**（1–3 周） | **最高（只要浏览器能播的都能抓）** | ✅✅ | ✅✅ | ✅✅ | 一次性开发 + 本地算力；LLM <¥1/视频 | 追求覆盖/隐私/长期复用 |

### 推荐路径（按用户「尽量覆盖更多平台」的诉求）

1. **起步（今天就能用）**：装 **沉浸式翻译** 覆盖 B站/YouTube/Netflix 等实时双语字幕；用 **BibiGPT 或通义听悟** 负责「逐字稿 + AI 总结」（含抖音）。
2. **进阶（要 B站高质量逐字稿）**：用 **B站字幕接口/油猴脚本** 直接抓官方/AI 字幕，导出 SRT，再丢给 **Kimi/DeepSeek** 总结——成本最低、质量最高。
3. **终极（要覆盖抖音及无字幕视频 + 隐私可控）**：自研或直接用 **WhisperLiveKit**（Chrome 扩展 + 本地 Whisper）作为 L1/L2 底座，再接 LLM API 完成 L3。这套能覆盖「浏览器能播的一切」，且音频不出本机。

## 8. 待确认问题

1. **优先级取舍**：你更看重「实时字幕的即刻性」还是「总结质量的深度」？（决定是主打扩展实时字幕，还是主打文件式转写+LLM）
2. **本地算力**：是否接受本地部署（Whisper）？本机是否有 NVIDIA 独显（≥6GB 显存）？这直接决定全自建方案是否可行、是否流畅。
3. **抖音覆盖的期望**：抖音无稳定字幕接口，只能「音频捕获 + ASR」或第三方在线工具，是否接受其准确率与延迟折损？
4. **可接受的月度成本**：能接受 0 元（纯免费额度）/ ~¥50/月（订阅 Pro）/ 仅付 LLM token（<¥1/视频）哪一档？
5. **隐私敏感度**：视频内容是否敏感到必须用本地 ASR/本地 LLM（不上传云端）？若可接受云端，方案选择会多很多。
6. （附加）是否需要**批量/长期留存**逐字稿（如建立个人知识库/Notion 同步）？这会倾向 BibiGPT 这类带笔记同步的工具。
